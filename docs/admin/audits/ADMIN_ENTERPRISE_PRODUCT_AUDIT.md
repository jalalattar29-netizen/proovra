## The short answer

`/admin` is **not** exclusively Platform Admin. Of the 74 parameter-free GET endpoints the admin console consumes, **37 are genuinely platform** (an ordinary organization owner is refused) and **32 are ordinary customer-tenant endpoints** that any organization owner can call. 11 pages under `/admin` administer *the operator's own active workspace*, not the platform — and a platform administrator who is not a member of a customer workspace receives `404` from them, so they cannot be used to administer any customer at all.

The codebase already knows this: all 11 carry a `WORKSPACE` chip in the console navigation and an on-page notice reading *"Workspace-scoped surface. This page administers your own active workspace — not the platform."* The remaining question is placement, not disclosure — and the register's stated reason for keeping them (`moving it would widen the audience`) is obsolete, because `/security-center/sso` already exposes the same endpoint to every `SECURITY_CENTER_VIEW` holder.

### PV-AUD-001 — Identity Audit 'Actor' column is fabricated from the query filter

**P1_TRUST_OR_OPERATIONAL** · FALSE_ATTRIBUTION · audience: WORKSPACE_SECURITY_ADMIN (page is gated PLATFORM_ADMIN)

- **Route** `/admin/identity/timeline`
- **Visible element** Table column 'Actor'
- **Frontend** `apps/web/app/(app)/admin/identity/timeline/page.tsx:260-286`
- **Endpoint** `GET /v1/admin/identity/timeline`
- **Backend** `services/api/src/routes/admin-identity.routes.ts:1051-1060`
- **Authority** requireIdentityAdmin (tenant OWNER/ADMIN or identity.org_policy.read) · **Plan** any

**Observed.** The projection sets actorUserId: q.subjectUserId ?? null. With no subjectUserId filter every row carries null and the page renders 'System'. With ?subjectUserId=<X> every row instead claims X as the actor, whoever really acted.

**Expected.** The Actor column shows the user who performed the event, or an explicit 'unknown' when attribution was never recorded.

**Code evidence.** admin-identity.routes.ts:1055 `actorUserId: q.subjectUserId ?? null`; page.tsx:275 `actorType: e.actorUserId ? "HUMAN" : "SYSTEM"` launders 'unknown' into 'System' even though presentActor (apps/web/lib/audit/auditPresentation.ts:106-125) has a correct UNKNOWN_LEGACY branch.

**Runtime evidence.** GET /v1/admin/identity/timeline?teamId=<northwind>&limit=5 -> every row actorUserId=null. Same query with &subjectUserId=0adf...0002 -> the identical rows return actorUserId=0adf...0002. The sso_health_checked row was in fact performed by 0adf...0001.

**Root cause.** The route projects the request filter instead of the stored actor. The writer (identity-operations-completion.routes.ts:464) records the actor only inside the details JSONB, never in the queryable SecurityEvent.userId column, so no correct value is available to project either.

**Operator risk.** The surface an operator opens to answer 'who changed our SSO' answers with a value derived from their own filter. On this fixture 100% of rows attribute to 'System'.
**Security / data risk.** Audit-integrity: a compliance timeline that misattributes actions cannot support an investigation or an access review.

**Fix.** Persist the acting user in SecurityEvent.userId at write time and project that column. Keep presentActor's UNKNOWN_LEGACY branch for historical rows rather than defaulting them to SYSTEM.
**Dependency.** Requires a backfill decision for existing rows whose actor lives only in details.actorUserId.
**Blast radius.** One route projection plus the emit sites that omit userId.

**Acceptance proof.** GET the timeline with and without subjectUserId; the actor of a known event is the same in both, and equals the user who performed it.

### PV-OD-001 — Is /admin the PLATFORM console, or the ADMINISTRATIVE console?

**Current behaviour.** 47 routes sit under /admin behind requiredActiveSpace PLATFORM_ADMIN. 25 are platform-only at runtime, 11 are purely tenant administration of the operator's own active workspace, 8 have no param-free GET to classify this way, and 3 are inconclusive. Every one of the 11 already carries an explicit WORKSPACE chip in the console navigation and an on-page notice reading 'Workspace-scoped surface. This page administers your own active workspace — not the platform.'

**Affected audiences.** PLATFORM_ADMIN_ONLY, WORKSPACE_ADMIN, WORKSPACE_SECURITY_ADMIN, ENTERPRISE_ORGANIZATION_ADMIN

- **Option A** — Move the 11 tenant pages out of /admin into the workspace/organization families (e.g. /security-center/*, /organizations/:id/admin/*). /admin then means the platform, without exception.
- **Option B** — Keep them and give each a tenant selector, so /admin means 'the platform, or a customer tenant I have explicitly chosen'. This is the only option that makes them useful to a platform operator who is not a member of the customer workspace — today they answer 404 for exactly that person.
- **Option C** — Keep them exactly as they are and rely on the WORKSPACE chip plus the scope notice, accepting that they administer only the operator's own workspace.

**Security trade-off.** A is neutral-to-positive: the API is already tenant-gated, and the capability is already reachable outside /admin via /security-center/sso, so moving does not widen anything. B widens materially — it requires cross-tenant identity administration, which does not exist today and would need its own authority, step-up and audit design. C changes nothing.
**UX trade-off.** A gives one home per capability. B is the only option that delivers what the URL currently promises. C leaves an operator reading 'Platform admin' above a page that administers their own workspace — mitigated but not removed by the notice.
**Operational trade-off.** A is a route move plus redirects and navigation updates. B is a feature. C is free.

**Recommendation for PROOVRA.** Option A. The disposition register's stated reason for keeping them ('the platform gate is currently STRICTER than the API and moving it would widen the audience') is obsolete: /security-center/sso already exposes the same endpoint to every SECURITY_CENTER_VIEW holder, and both org-owner and workspace-admin hold it. Keeping the pages under /admin therefore restricts nothing and costs comprehension. Option B is defensible only if cross-tenant identity administration is genuinely wanted as a product.

**Question requiring approval.** Do we move the eleven workspace-scoped pages out of /admin (A), build a tenant selector so they become genuinely cross-tenant (B), or accept the current labelled state (C)?

## The sixteen mandatory questions

**1. Is `/admin` exclusively Platform Admin, or mixing platform and customer administration?**

Mixing. 32 of 74 probed endpoints are ordinary tenant endpoints, and 11 pages administer the operator's own workspace. Proven by the cross-tenant experiment above.

**2. Which `/admin/**` pages should move?**

The 11 listed under Route placement. Recommendation and alternatives in `PV-OD-001`.

**3. Which Enterprise/Security pages outside `/admin` should move into Platform Admin?**

None. Every surface outside `/admin` that was probed is tenant- or organization-scoped and correctly placed. The movement in this codebase is one-directional: tenant administration has drifted *into* `/admin`, not platform administration out of it.

**4. Is `/security-center/mfa-recovery` correctly placed?**

Yes, on audience. It is `WORKSPACE_SECURITY_ADMIN`: `authorizeMfaAdminScope` requires the actor to be an ACTIVE OWNER/ADMIN of the target workspace and the subject to be an ACTIVE member of that same workspace, with anti-enumeration concealment. It is not self-service and not platform support — a platform admin cannot cross a tenant boundary with it. Its copy says exactly this. Two defects remain: `PV-COPY-002` (empty state names the wrong object) and `PV-API-001` (the list route bypasses the module's own gate). Note the page gate asks only for `SECURITY_CENTER_VIEW` while the API requires OWNER/ADMIN, so a member with the capability but not the role opens the page and sees a concealed-empty queue.

**5. Are SCIM, SAML, Identity Providers and Access Reviews correctly placed?**

No — all four are tenant administration under a Platform-Admin URL and gate (`PV-PLACE-001`), and identity-provider administration exists twice (`PV-DUP-001`). Their *authority* is correct and their *scope disclosure* is correct; only the route family is wrong.

**6. Why is each visible disabled control disabled?**

43 give no reason at all (`PV-DIS-001`, 26 routes). Where a reason is given it is good: SCIM's **New token** carries *"Issuing a token is part of the Enterprise plan. Existing tokens can still be revoked."*; Access reviews' **Regenerate queue** carries *"This surface is part of the Enterprise plan, and the workspace you are acting in does not carry it. Switch into an Enterprise workspace to use it here."*; Archive Tiers' **Move tier** carries *"Enter an evidence ID first."*

**7. Which controls click but produce no observable result?**

None were found among the executed families. Every control executed produced a request, a durable effect or an explicit refusal, and the Resolve family re-reads authoritative state after success. Unexecuted mutations are registered under NEEDS_RUNTIME_PROOF rather than claimed either way.

**8. Does every Resolve action truly resolve its named source condition?**

Yes — proven by executing Resolve against one incident of every kind: `IDENTITY_SECURITY` 200 (`OPERATOR_DECISION`), `REPORT` 200 (`SOURCE_TRUTH`), `RECONCILIATION` 409 `CONDITION_STILL_ACTIVE`, `EVIDENCE_INTEGRITY` 409 `CONDITION_STILL_ACTIVE`, `WORKER` 409 `CONDITION_NOT_DIRECTLY_RESOLVABLE`. The platform refuses rather than falsely succeeding, and audits the outcome. The one defect is the failure *message*, which states the wrong reason for one of the two refusal codes (`PV-OPS-001`).

**9. Which UI strings expose database/API vocabulary?**

198 across 63 routes (`PV-LANG-003`), plus generated labels that mangle acronyms on 104 of 382 event types (`PV-LANG-001`).

**10. Which pages show developer language to operators?**

`/admin/platform/automation` (bare enum allowlists plus *"Adding a value requires a coordinated DB migration"*, `PV-ALLOW-001`); `/integrations` (raw `reason=feature_flag_off apiKeySecret=ok` diagnostics, `PV-COPY-001`); `/evidence-lifecycle/destruction` (*"Permission required: DELEGATED_ADMIN"*, `PV-STATE-001`); `/admin/identity/permission-matrix` (raw dotted permission ids as list text).

**11. Which pages have truthful plan/refusal states?**

The platform gate is exemplary: a Free personal user opening any `/admin` route sees *"Platform administrator only — Platform admin elevation is required for this surface"* with a return path, and **no admin API call is made at all**. Plan refusals are truthful too: `/admin/identity/access-reviews` renders its 402 as a refusal with an upgrade path, and the organization console answers `402 ENTERPRISE_FEATURE_REQUIRED` with an `upgradeCta`. Authorization is correctly evaluated *before* entitlement, so a non-member learns nothing about a workspace's plan.

**12. Which pages show empty when the real state is error/refusal/unavailable?**

`/evidence-lifecycle/destruction` shows *"No destruction requests pending"* while the list request is refused (`PV-STATE-001`); `/evidence-lifecycle/archive`, `/evidence-lifecycle/webhooks` and the `/evidence-lifecycle` index also take a 403 with no visible refusal. Twelve further routes drop a refused read silently for a VIEWER, mostly in the organization console.

**13. Which backend operator capabilities lack UI?**

Not established. 1033 of the 1107 known backend routes were not classified as UI-complete / API-only / worker-only in this pass. This is registered as unfinished rather than answered.

**14. Which UI controls lack a backend authority?**

None among the traced controls: every frontend request resolved to a registered handler with a named authority. 17 call sites resolved to `UNRESOLVED` in static analysis because their path is fully interpolated; those are listed in the JSON per page.

**15. Are all navigation and return journeys coherent?**

Largely yes. All 141 routes returned 200 for a platform admin with no navigation errors; redirects are purposeful (`/people`→`/teams/:id`, `/reviewer-ops/queue`→`/review`, `/settings/security/saml`→`/security-center/sso`, `/organizations/:id/admin`→`/overview`). Defects: a duplicated breadcrumb crumb (`PV-NAV-001`), 33 routes with a duplicate `<main>` landmark that breaks the skip-link contract (`PV-A11Y-001`), and 3 heading-order jumps.

**16. What exactly must remediation change?**

In order: (1) `PV-AUD-001` stop fabricating the audit Actor column; (2) `PV-AUD-002` fix the unconditional 500 in the effective-retention resolver; (3) resolve `PV-OD-001` and act on `PV-PLACE-001`/`PV-DUP-001`; (4) `PV-STATE-001` and `PV-DIS-001` so refusals and disabled states are truthful everywhere; (5) `PV-LANG-001`/`PV-LANG-003`/`PV-ALLOW-001` for operator language; (6) `PV-A11Y-001`; (7) the P3 register.

## Method

One discovery pass, one source-trace pass, one targeted runtime pass, one reconciliation pass.

- **Discovery by authority, not URL prefix.** All 165 authenticated pages were resolved through the repository's own canonical instruments — `apps/web/lib/navigation/routeRegistry.ts`, `apps/web/components/admin/adminNavigation.ts` and the backend route registrations — using the existing `apps/web/scripts/admin-inventory.mjs` extractor widened from `/admin` to the whole authenticated tree. No competing registry was created. A page is in scope if it sits in a mandated family, requires an administrative capability, or calls an endpoint with an administrative authority; the 24 excluded pages are enumerated in the JSON.
- **Live authority probing.** Endpoint classification is not inferred from folder or handler name. Four seeded personas called each endpoint and the response decided the class.
- **Runtime observation.** A real Chromium session signed in as each persona and walked all 141 routes, recording headings, every visible control with its enabled state and disabled reason, landmark structure, the states each page claims, every `/v1` call with its status, and console errors.
- **Isolation.** Disposable PostgreSQL and Redis containers, the repository's sanctioned `scripts/local-fixture-env` allowlist, and its assertion that no configured host is non-local. `services/api/.env` — which holds production credentials — was never read by any process started here.

### Hypotheses tested and disconfirmed

Recorded because a rejected hypothesis is a result:

- **Workspace enumeration via MFA recovery.** The list route answers 403 with a distinguishable code where its siblings answer 404. Tested against a real team the caller is not in, another user's personal workspace, and two non-existent UUIDs — all four returned the byte-identical 403. No oracle. Downgraded to a consistency defect (`PV-API-001`).
- **A 500 rendered as a false governance assurance.** `/governance/retention` shows *"No retention policy applies. The default (indefinite retention) is in effect"* on the same load as a 500. Reading the source showed that sentence comes from a different, working endpoint, and the failing panel renders a proper failure card. The 500 is real (`PV-AUD-002`); the false-assurance claim is not.
- **The Organization Admin console is broken for its own operator.** Every `/v1/orgs/<org>` call returned 403 for the org owner. The cause is that the fixture seeds no organization memberships for the organization-shaped organizations; probed against an organization the caller genuinely belongs to, 8 of 9 endpoints returned 200 and the ninth a clean 402. Registered as NEEDS_RUNTIME_PROOF, not as a defect.
- **SCIM entitlement gaps.** Create, rotate and the protocol surface enforce the Enterprise `ssoScim` entitlement; list and revoke deliberately do not, each with a documented reason (a customer must always be able to see and destroy a credential that already exists, including after a downgrade). Correct as designed.
- **An allowlist offering an unimplemented action.** `automation-actions.service.ts` says `WEBHOOK_DELIVERY_INTERNAL_ONLY` is "intentionally NOT implemented". The same file dispatches it and the live CHECK constraint permits it. The comment is stale (`PV-DOC-001`); the action works.
- **Truncated data behind `WEBHOOK_DELIVERY_INTERNAL_ONL`.** The value is 30 characters in source, in the live CHECK constraint, in a `varchar(60)` column, and renders complete and unclipped at 320, 768 and 1440px. Display clipping under some other viewport, not data loss.

### What was deliberately not done

No product file was modified by this audit, no migration created, no commit made, and Production was never contacted. The working tree **did** change during the audit — see [Baseline integrity](#baseline-integrity) — but by a concurrent session, not by this one. The only repository paths this audit wrote are the two artifacts named above; everything else it created lives in disposable containers and a scratchpad outside the repository.
