# Phase M1 — Offline Verification Ecosystem — Closure Report

**Audience:** product engineers, procurement, customer-success.

---

## 1. Verifier architecture

Two surfaces, ONE bounded algorithm:

```
┌────────────────────────────┐         ┌────────────────────────────┐
│  packages/offline-verifier │         │   apps/offline-verifier    │
│  ─ src/verifier-core.ts    │ shares  │   ─ index.html             │
│  ─ src/result-schema.ts    │ ←─────→ │   ─ verifier-browser.mjs   │
│  ─ src/node-adapter.ts     │  schema │     (re-implements same    │
│  ─ bin/proovra-verify.mjs  │         │      algorithm against     │
└────────────────────────────┘         │      WebCrypto + JSZip)    │
              │                        └────────────────────────────┘
              │ npm publish (future)
              ▼
    Third-party CLI usage
    via `npx @proovra/offline-verifier`
```

The core takes a `PackageReader` + `CryptoAdapter` interface so the same code path works in Node and in the browser. The browser app keeps a small inline re-implementation (single file, no bundler) so the static page is a single artifact that any operator can self-host without npm installs.

## 2. Package support matrix

| Package origin | Behaviour |
| --- | --- |
| Generated by current worker (P3.1.1 + M1) | All sections evaluated. `custody/attestations.json` and `signers/signer-registry-snapshot.json` are structurally checked. `OFFLINE-VERIFICATION.md` ships inside the ZIP. |
| Generated before P3.1.1 (no attestation files) | `custodyAttestations.status = "missing"` + `PRE_P3_1_1_PACKAGE_DETECTED` warning. Old packages NEVER hard-fail. |
| Tampered (file content modified after signing) | `package.checksumsStatus = "mismatch"` + per-file `checksumFailures[]` + `overall.status = "failed"`. |
| Missing required file from index | Specific file recorded in `checksumFailures` with `reason="missing"`. Still bounded — never crashes. |
| Malformed ZIP | Safe failure path; CLI exits 2 with bounded error code. |

## 3. CLI summary

`packages/offline-verifier/bin/proovra-verify.mjs`:

- Reads the ZIP via `adm-zip`.
- Recomputes SHA-256 via `node:crypto`.
- Verifies the Ed25519 package signature via `node:crypto.verify`.
- Emits a human-readable summary by default; `--json` for machine output; `--out file.json` to persist.
- Bounded exit codes: 0 / 1 / 2 (per spec).
- NEVER prints raw evidence content, secrets, or signatures in clear.

## 4. Browser/static verifier summary

`apps/offline-verifier/index.html` + `verifier-browser.mjs`:

- Single static page. No build step. No bundler.
- Loads JSZip from a pinned CDN URL with Subresource Integrity (`sha384` hash).
- Reads file via the browser File API.
- SHA-256 via `crypto.subtle.digest`.
- Ed25519 verification via `crypto.subtle.verify("Ed25519", …)` when the browser supports it; otherwise reports `unsupported` (no fake-verified path).
- Privacy notice at top of page: "Verification runs locally in your browser. The selected ZIP is never uploaded."
- Result can be downloaded as JSON (`proovra-offline-verification-result.json`).

## 5. Verification result schema

`PROOVRA_OFFLINE_VERIFICATION_RESULT_V1` — fully documented in `docs/verification/offline-verification-result-schema.md`. Bounded enums for every status field. Bounded code lists for warnings + limitations. The verifier ALWAYS includes the standing limitations:

- `NO_LEGAL_ADMISSIBILITY_CLAIM`
- `NO_AUTHORSHIP_CLAIM`
- `TSA_REQUIRES_EXTERNAL_RFC3161_VERIFICATION`
- `OTS_REQUIRES_BITCOIN_NETWORK`

These are baked into the schema, not editorial notes.

## 6. Package integration summary

Every newly generated Verification Package now contains `OFFLINE-VERIFICATION.md` (bundled by the worker package builder). The file:

- Names the CLI command.
- Lists exit codes.
- Describes what is verified offline and what is not (with the same honest limitations as the API result).
- Carries no legal claims.

Existing files (`package-manifest.json`, `package-manifest.sig`, `package-manifest-public-key.pem`, `package-checksums.json`, `custody/*`, `signers/*`, `evidence/*`, `intelligence/*`, `timestamps/*`, `opentimestamps-*`) are UNCHANGED in path, content schema, or append order.

## 7. Public Verify / Report / Operations surfacing summary

P3.1.1 deliberately stopped short of mounting offline-verifier badges in the live UI. M1 adds the in-package README; the live UI links are an explicit follow-up to keep this phase deliverable in a single coherent slice (see §13).

## 8. Security / privacy summary

- **CLI**: makes no network calls. Sanitises ZIP paths against path-traversal (`..`, absolute paths). Caps text-decode at 32 MB per file. Never echoes evidence content. Bounded exit codes.
- **Browser**: makes only ONE network call ever — the initial JSZip script-tag load via CDN with Subresource Integrity. The file is read locally and never POSTed. Privacy notice is at the top of the page.
- **Both** scrub any path before reading. Both refuse to claim "verified" for any signature path they couldn't actually verify cryptographically. Both report `unsupported` rather than `failed` for surfaces that need external tooling.

## 9. TSA / OTS limitations

Honest by design. Documented in:

- `docs/verification/offline-verifier.md` §3
- `docs/verification/offline-verification-result-schema.md` (the bounded `limitations[]` enum)
- `OFFLINE-VERIFICATION.md` bundled inside every new package
- `docs/public/offline-verification-user-guide.md` §5

The verifier reports `tsaStatus="unsupported"` with `tsaDetail="rfc3161_external_verification_required"` when a TSA token is present. It reports `otsStatus="unsupported"` with `otsDetail="calendar_network_required"` when an OTS proof is present (unless the companion file says `PENDING`, in which case `otsStatus="pending"`).

## 10. Custody attestation verification summary

- Structural integrity of every attestation envelope: ✅ verified offline.
- Bounded reporting of `attestationsExpected`, `attestationsChecked`, `attestationsVerified`, `failures[]`: ✅
- Cryptographic signature verification of attestations against the signer's public material: ❌ requires the live PROOVRA API endpoint (`/v1/operations/custody-attestations/:id/verify`) because the public material is referenced (not bundled). The verifier explicitly reports `custodyAttestations.status = "unsupported"` with the bounded limitation code so consumers see the honest gap.
- Old packages without attestation files: ✅ `missing` (NEVER `failed`).

## 13. Remaining blockers / follow-ups

**None for M1 acceptance.** Tracked as follow-up (NOT part of this closure):

1. **Mount a public `/offline-verifier` route on `apps/web`** that ships the static page as part of the main web build. Today the page lives at `apps/offline-verifier/index.html` and is operator-self-hostable; mounting it on the web app is a small Next.js public-folder copy.
2. **`npm publish`** of `@proovra/offline-verifier`. The package is `"private": true` in this repo. Switching to public publishing is a release-engineering decision.
3. **Inline custody-attestation public key** inside packages (post-M1). Today the signer's public material is referenced; bundling it would make custody attestation signature verification fully offline. This is a deliberate trade-off — we don't bundle public material because rotation would make stale packages misleading.
