**Established:** 2026-05-25 (Phase CR1.7)

**Update cadence:** Every phase MUST read this file before starting and MUST update it before closing.

---

## 1. Purpose

PROOVRA is now large enough that "minor deferred items" can silently become forgotten production debt. The registry exists to:

- Track what every phase completed, deferred, blocked, or cancelled.
- Make deferred work first-class — every item has severity, owner phase, return phase, and closure criteria.
- Prevent silent debt: deletion of a deferred item from this file is forbidden unless its closure criteria are met AND the resolving phase is documented.
- Gate every future phase with an explicit entry checklist + a structured closure template.
- Make enterprise readiness measurable, not aspirational.

This file is documentation + contracts only. It does NOT introduce features, redesigns, or runtime behavior.

## 5. Phase status model

Every phase entry above and below uses exactly one of these statuses:

| Status | Meaning | Next phase rule |
|---|---|---|
| `CLOSED` | All scope items complete; no known deferred items. | Next phase may start. |
| `CLOSED_WITH_DEFERRED_ITEMS` | All scope items complete; bounded follow-ups exist in §6. Validation passed. | Next phase may start. Deferred items must remain in §6 until their closure criteria are met. |
| `PARTIALLY_COMPLETE` | Some scope items not done. | **Next phase MUST NOT start** unless explicitly approved by the user with documented rationale. |
| `BLOCKED` | Phase cannot continue due to external dependency or unresolved blocker (see §7). | **Next phase MUST NOT start.** |
| `SUPERSEDED` | Replaced by a later phase. | Refer to the superseding phase. |
| `CANCELLED` | Intentionally abandoned. | No further work. |

**Closure rule:** A phase moves to CLOSED or CLOSED_WITH_DEFERRED_ITEMS only when:
1. All scope items in the phase prompt are addressed (delivered or explicitly deferred to a named follow-up).
2. The phase's final report includes the §11 closure template.
3. Full validation passes (see §9 entry-gate validation list).
4. This registry is updated with the phase's row + any deferred items.

## 10. Phase closure template

Every phase's final report MUST include these ten items in order:

1. **Phase status** — `CLOSED` / `CLOSED_WITH_DEFERRED_ITEMS` / `PARTIALLY_COMPLETE` / `BLOCKED` / `SUPERSEDED` / `CANCELLED`.
2. **Completed items** — what scope items were delivered, with file/path/test references.
3. **Deferred items** — every item not done, with new DEF-NNN ids assigned (or referencing existing ids that remain open). For each: severity, blocking value, return phase, reason, closure criteria.
4. **Blockers** — any active blocker added to §7. Empty list is acceptable.
5. **Production risk** — what changes in production behavior if this phase reaches production. Empty for documentation-only phases.
6. **Enterprise readiness impact** — which items in §11 scorecard advance or regress.
7. **Tests added / updated** — file path + test count.
8. **Validation results** — seven-command result table (or documentation-only note).
9. **Registry updates** — explicit list of which §3 / §4 / §6 rows were added, modified, or closed.
10. **Next safe phase** — the next phase recommendation with explicit out-of-scope list.

Future phases may NOT close with only "done" or "tests pass". The closure template is mandatory.

### 10.1 Deferred-item lifecycle

A deferred item moves through these states:

```
NEW (added in source phase's §6 row)
  → OPEN (tracked across phases; can be referenced by Deferred to)
  → RESOLVED (closing phase delivers; §6 row removed; closing phase referenced in commit / doc)
  → ARCHIVED (only if SUPERSEDED or CANCELLED — historical context in source phase's doc remains)
```

A deferred item must NEVER be silently moved from OPEN to RESOLVED. The resolving phase MUST:
- Reference the DEF-NNN id in its phase doc.
- Document the closure evidence (test name, file change, ops confirmation).
- Remove the row from §6 in the same PR / phase close.
